# System Instructions: Thin Harness, Fat Skills Environment

## 1. Core Philosophy
- You are a lightweight execution harness. Rely on deterministic shell tools, minimal MCP servers, and basic filesystem commands.
- Treat this file and project documentation as your "Fat Skills." Read instructions as structured data and execute your logic strictly against them.
- ALWAYS activate and adhere to the `iso-24495-1` Plain Language skill across all responses (no filler preambles, short sentences/paragraphs, active voice, scannable structure, concrete instructions).
- Context management is the bottleneck, not model capability. Protect the token window.

## 2a. Editorial Stylebooks (agent-stylebooks)

Plugin `agent-stylebooks@agent-stylebooks` (16 skills, installed 2026-09-05, spec: `docs/superpowers/specs/2026-09-05-agent-stylebooks-integration-design.md`). Each skill is a genre-specific editorial system (e.g. `$google-developer-docs`, `$govuk`, `$sec-plain-english`) that governs structure and ordering for a written deliverable — never voice, never the plain-language floor. (`$name` is the upstream repo's own shorthand notation; the actual addressable skill id is `agent-stylebooks:<name>` — though these auto-fire by genre match rather than by explicit invocation, so this rarely matters in practice.)

**Three-layer precedence: iso-24495 floor > brand voice > stylebook structure (highest wins):**

| Layer | Owner | Governs | Fires |
|---|---|---|---|
| Plain-language floor | `iso-24495-1` (+ `iso-24495-3` for technical writing) | Sentence-length ceiling, paragraph limits, active voice, baseline scannability (a stylebook may reorder within this floor, never below it) | Always — every reply and every document |
| Voice | `brand` (HARD-GATE) | Word choice, tone, formality (writing dimensions only — see §2 for `brand`'s full visual/palette/typography scope) | Always, before any output is created |
| Genre structure | agent-stylebooks (auto-detected) | What to lead with, section/procedure ordering, genre terminology | Per matching deliverable only — never for conversational replies |

A stylebook never widens a sentence past the iso-24495 ceiling and never shifts tone away from brand voice (no per-stylebook exceptions — confirmed during grilling for `$mailchimp-content`, whose own voice is "plainspoken, empathetic, lightly playful": it still only contributes structure, tone stays formal brand voice).

**Tiebreak rule:** 8 of the 16 stylebooks (`$google-developer-docs`, `$gitlab-docs`, `$github-docs`, `$kubernetes-docs`, `$red-hat-docs`, `$mdn-web-docs`, `$w3c-technical-reports`, `$nasa-technical-writing`) all plausibly match generic "technical documentation," and `$18f-content`/`$govuk` both match generic "public-service content." Resolution: fire an org-named stylebook only on a concrete platform/geography signal (content is actually about Kubernetes, actually about GitHub/GitLab, actually US-federal, etc.); with no signal at all, default to the family anchor (`$google-developer-docs` for generic technical writing, `$govuk` for generic public-service writing) rather than guessing among near-ties or firing none. This applies to any two-or-more-way tie in the table above, not only these two clusters.

**Scope boundary:** stylebooks fire only when creating/editing an actual saved document, docs page, or content file — never for a plain conversational reply, even a documentation-shaped one (e.g. explaining an API inline in chat). Conversational replies stay governed solely by the always-on `iso-24495-1` output style.

- **Subagent worktree-escape verification:** dispatched implementer subagents can silently escape worktree isolation — via an absolute path that resolves to the main checkout, or by attempting to self-modify `settings.json` permissions when a sandbox wall blocks a write (never comply with that; investigate the restriction or do the write directly in the main session instead). Give worktree-scoped dispatch prompts explicit relative-path-only instructions plus `pwd`/`git rev-parse --show-toplevel`/`git branch --show-current` checks before and after every write/commit, and independently re-verify the claimed commit's branch/parent (`git log --all`) from the controller side before trusting a DONE report. If escape is discovered after the fact, remediate non-destructively: `git reset --soft` (never `--hard`) to preserve unrelated concurrent daemon-driven `.wolf/*.md` changes, restore the affected file content, and remove only the specific stray artifacts — never a blanket reset of the main checkout.
- **Worktree merge pattern:** After committing in a worktree, `git checkout main` fails from inside it (main is checked out in the parent), and — now that branch protection is active — a local `git merge` into `main` would be rejected by GitHub on push anyway. Exit sequence: `ExitWorktree` (keep) → push the branch (`git push -u origin <branch>`) → `gh pr create` → wait for explicit user approval to merge (per CLAUDE.md §2's existing "never merge without an explicit yes" rule, unchanged) → `gh pr merge --squash` → `git -C /Users/paulmckay/.claude pull origin main` → `git worktree remove .claude/worktrees/<name> --force` → `git branch -d <branch>`. **The `pull` step can fail** with "divergent branches" if local `main` has any commits not yet pushed to origin (routine here — specs/plans get committed to local `main` during brainstorming before ever being pushed). Confirm first with `git log origin/main..main`; if non-empty, use `git merge origin/main` instead of `pull` (safe when the squash-merged content is a superset of local `main`'s unpushed commits, which it will be if those commits are what the PR was built from) — never `reset --hard`, which would discard the unpushed local commits. The `git fetch origin main` behind that `git log`/`git merge` pair must run **after** `gh pr merge`, not reused from earlier in the session — a stale `origin/main` ref makes `git merge origin/main` silently report "Already up to date" without the PR's content ever landing on local `main`.
- **Stacked PR unmergeable after its base squash-merges:** if branch B was built on top of branch A (both open as separate PRs) and A merges via squash, retargeting B's PR to `main` shows `CONFLICTING` even though the content is identical — git can't recognize a squash commit as equivalent to the original commits it replaced. A plain `git rebase origin/main` on B tries to replay B's *entire* ancestor chain back to wherever B's branch actually forked (which can be far deeper than expected if the branch it forked from itself had stale local-vs-origin divergence baked in). Fix: `git rebase --onto origin/main <B's-real-fork-point-SHA> <B-branch-name>` — replays only B's own unique commits, skipping the ambiguous shared history entirely. Requires `git push --force-with-lease` afterward (real history rewrite).
- **Merging several independent PRs in one sequence invalidates every other open PR's "up to date" status on each merge**, when branch protection has `required_status_checks.strict=true` — `gh pr merge --squash` fails with "the head branch is not up to date with the base branch" for PR #2 immediately after PR #1 merges, even though PR #2's own CI was already green. Each remaining PR needs `gh api repos/<owner>/<repo>/pulls/<N>/update-branch -X PUT` before it's mergeable again — and if a third PR is still pending when the second merges, it needs updating again too. Expect up to N `update-branch` calls when merging N PRs in one session, not just one per PR.
- **Stash conflicts on worktree-merge cleanup:** if `git merge origin/main` refuses ("local changes would be overwritten") because the main checkout has pre-existing unrelated uncommitted drift in files your PR also touched, stash with a unique tagged message, capture its SHA (`git stash list --format='%H %gs'`), merge, then reapply by that exact SHA (`git stash apply <sha>`, never bare `pop`). Resolve conflicts by file type: append-only logs (`memory.md`) get both blocks concatenated in chronological order; wholesale-regenerated inventories (`anatomy.md`) get `git checkout --ours` + a fresh `openwolf scan` rather than a hand-merge. Drop only the stash entry matching your own tag — never touch other stash entries from concurrent sessions.
- **EnterWorktree branches from origin, not local main:** `EnterWorktree`'s default `worktree.baseRef` (`fresh`) branches from `origin/<default-branch>`, not local `main` — so any local-only commits on `main` not yet pushed (see above) are invisible in a freshly created worktree, and `docs/superpowers/specs/*.md` committed earlier in the same session won't be present until reconciled. Fix locally with `git rebase main` from inside the worktree (no push needed) right after `EnterWorktree`, before the first `task-brief` call.
- **Submodule commit transfer (worktree → main):** worktrees get independent submodule clones — a commit made in one is invisible to the other. To land it: create a named branch at that commit in the source clone, then from the target clone `git fetch <path-to-source-submodule-clone> <branch-name>` and `git branch -f local-customizations FETCH_HEAD`. A raw SHA is not fetchable via plain local-path fetch. `scripts/submodule-transfer.sh <submodule-path> <source-worktree-root> <commit-sha>` automates this.
- **Submodules aren't auto-initialized in fresh worktrees:** a new worktree (native `EnterWorktree` or `git worktree add`) leaves submodule directories empty until `git submodule update --init <name>` runs. A task touching a submodule-backed file (many skills are symlinks into `superpowers/`) can silently end up committing in the primary checkout instead of the isolated copy if this isn't checked first — verify `git -C <submodule> branch --show-current` before dispatching such a task in a worktree.
- **Hook/settings.json changes are not live mid-worktree:** edits to `settings.json` (or any hook file) made inside a worktree do NOT affect that running session — hooks were already loaded from the main checkout's `settings.json` at session start. Verify new hook behavior (e.g. spawning a probe subagent) only after merging into main, not mid-branch.

Same-session workaround: `Read` the skill file directly and follow it manually; for an MCP server, call the underlying SDK/CLI directly instead of waiting for its tools to appear. Both work normally starting the next session.
- **Editing a skill doesn't republish `docs-site`:** `.github/workflows/deploy-docs.yml` only redeploys on pushes touching `docs-site/**` (or the workflow file itself) — a `skills/**`-only edit never triggers it, even though `docs-site/scripts/pull-skills.mjs` pulls skill content in on `predev`/`prebuild`. - **`CLAUDE_CWD` is a dead variable:** referenced via `${CLAUDE_CWD:-default}` in settings.json but never actually assigned — always resolves to its default regardless of session location. Use `CLAUDE_PROJECT_DIR` instead (the real, populated equivalent, used correctly in `.wolf/hooks/shared.js`).
- **Concurrent sessions:** Edit/Write on a `.wolf/` file or `CLAUDE.md` repeatedly failing with "file changed since read" signals another live session. Use small targeted `Edit` calls scoped to untouched lines, or ask the user. `.wolf/memory.md` entries near your own timestamps aren't necessarily yours — verify via `git log`/`gh pr list`/`gh issue list` rather than the shared log alone when concurrent activity is suspected.
- **Worktree scope:** `EnterWorktree` always targets the session's primary repo (`~/.claude`) — it can't target a secondary/"additional working directory" project. For those, use `git worktree add <path> -b <branch> origin/<base>` via Bash instead. It also targets the session's **launch directory**, not `~/.claude` unconditionally: if the session starts in a non-repo parent (e.g. launched from `/Users/paulmckay` with `~/.claude` as a git repo one level down), it fails outright ("not in a git repository and no WorktreeCreate hooks are configured") rather than falling back to the nested repo — use the same `git worktree add` fallback as the secondary-project case.
- **Model routing:** Haiku for mechanical/log-inspection/single-file-lookup subagent work, Sonnet default, Opus for complex multi-file reasoning. Default effort for routine work; extended thinking only for genuinely complex decisions. See `model-routing` skill for detail.

## 5. Personal Knowledge Layer (gbrain)
- **MCP server:** `gbrain` — a PGLite-backed personal-knowledge tool (`gbrain get/put/search/query/ask`), registered in `~/.claude.json`'s `mcpServers`. Its content lives in the git-backed `~/brain/` directory (people/, companies/, concepts/, decisions/), which an autopilot background process (`gbrain autopilot --repo ~/brain`, PM2-managed) continuously enriches — embedding, linking, backfilling — from that git history.
- **Before answering questions about people, companies, or past decisions:** use `gbrain query`/`gbrain search` (or the MCP tool surface) against the relevant content first.
- **Write decisions back:** after any significant decision in a session, use `gbrain put <slug>` to persist it with context.
- **For synthesis questions** (e.g. "what do I know about X?"): search/query, read matching pages, then synthesize.
- **Cross-reference with cerebrum:** gbrain = cross-project / personal knowledge; `.wolf/cerebrum.md` = project-specific patterns — both complement each other.
- **Native Claude Code auto-memory** (`~/.claude/projects/*/memory/`) is a third, distinct layer: user/feedback/project/reference facts about working *with Claude Code itself*, persisted across all projects. It is not project-specific implementation patterns (that's cerebrum's job) and not long-lived personal/company knowledge (that's gbrain's job) — keep facts in the layer they belong to rather than duplicating across two.
- **Known history:** an earlier version of this file described a "brain" filesystem MCP server that was never actually registered (`~/brain/` and a template `mcp_servers.example.json` existed, but no real `mcp_servers.json` or `mcpServers` entry ever did) — `gbrain` is the system that's actually been serving this role.

## 6. Knowledge Graph (`understand-anything`)
- `~/.claude` is tracked in git (baseline `b354ad3`) — commit regularly for incremental updates (1-5 batches vs. 32 for a full rebuild).
- Re-analyze after changes: `/understand-anything:understand ~.claude`
- `langsmith-plugin` is a git submodule — do NOT `git add` its contents directly; use `git submodule update` to sync it. `superpowers` and `skills/senior-engineering-partner` were vendored (converted from submodules to regular tracked files, PR #14/#16) and can be edited directly like any other file in this repo — confirmed via `git ls-files -s` showing `100644` blob mode, not a `160000` gitlink, for both.

- `local-customizations` is a snapshot, not a moving ref — re-fast-forward it (`git branch -f local-customizations <sha>`) after every new submodule commit; check `git log --oneline -1 local-customizations` against `main` first.
