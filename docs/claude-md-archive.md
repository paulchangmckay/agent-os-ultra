## 3. Infrastructure Layer (OpenWolf Integration)
- **GitHub repo renamed:** `paulchangmckay/brain` → `paulchangmckay/agent-os-ultra` (discovered 2026-08-19 via a `git push` redirect notice). Old remote URL still works via GitHub's redirect, but new PR/issue links use the new name — don't be confused if a URL doesn't match `.git/config`'s `origin` value.
- **Protocol enforcement rules:** See `.claude/rules/openwolf.md` — anatomy checks, buglog cross-references, and memory update rules live there.
- **Prevent re-reads:** PreToolUse hook blocks a re-read only if content is unchanged since last read this session (SHA-256 hash, mtime fallback >5MB) — never blocks the same read twice in a row; a `SessionStart` hook resets the read-history file every session. Upgraded from a 10-min-window heuristic 2026-08-19 (PR #69); a `PostToolUseFailure` hook also suggests the correct path on a failed Read/Edit with a wrong path.
- **Grilling gate hook:** `hooks/pre-skill-gate.js`/`hooks/post-skill-record.js` block invoking `writing-plans` unless `grilling` (or `/grill-me`) already ran this session — session-scoped via `.wolf/_skill-gate-<session>--<skill>.json` marker files. Real enforcement for the `brainstorming → grilling → writing-plans` gate, not just prose.
- **Local lint/secret-scan gate:** `.githooks/pre-commit` (`git config core.hooksPath .githooks`) runs shellcheck + eslint(security) + gitleaks on staged files pre-commit — enforcement counterpart to `secrets-and-key-rotation.md`/`frontend-web-security.md`. Config: `eslint.config.js`, `.shellcheckrc`, `.gitleaks.toml`. Tier 0, local only; missing tools warn-and-skip.
- **Git safety-rail hook:** `hooks/block-dangerous-git.sh` (PreToolUse/Bash) unconditionally blocks `push --force`/`push -f`, `reset --hard`, `clean -f(d)`, `branch -D`, `checkout .`, `restore .`, `--no-verify`, `--no-gpg-sign`, `commit.gpgsign=false` — no bypass flag, blocks even when the specific invocation is safe (e.g. force-pushing a clean rebase, or resetting to a commit already on origin). When blocked, use a non-destructive equivalent (`git branch -f` + checkout instead of `reset --hard`; a merge instead of a rebase to avoid needing force-push) rather than asking the user to disable it, unless there's truly no alternative.
- **Portable-repo hygiene:** See `.claude/rules/portable-repo.md` — no hardcoded absolute paths, no tracked generated artifacts, machine-specific values go in `settings.local.json` not `settings.json`. Complements the gitleaks gate above (that catches secrets; this catches paths/usernames that aren't secrets but still shouldn't be public). Added after the repo went public and a path audit found 12 files leaking `~`.
- **`subagent-driven-development`/`executing-plans` aren't Skill-tool dispatchable right now:** confirmed by trying both bare and `superpowers:`-prefixed names — both return "Unknown skill." This is the plugin-cache drift flagged at session start (`installed_plugins.json` records an older `superpowers` commit than the actual submodule HEAD). Workaround: the files still exist at `superpowers/skills/<name>/SKILL.md` — `Read` them directly and follow the instructions manually, including their referenced `scripts/*` helpers (`task-brief`, `review-package`), which work fine invoked directly via Bash. Don't block a subagent-driven-development execution on this.
- **`openwolf cron` has no custom script action:** the daemon only supports 4 built-in action types (`scan_project`, `consolidate_memory`, `generate_token_report`, `ai_task`) — confirmed via `openwolf cron --help`. A "run this periodically" need for a custom script must be a lifecycle hook (e.g. SessionStart) with its own timestamp-gate file, not a `.wolf/cron-manifest.json` entry.
- **`openwolf status`'s "Daemon: running" is not reliable — check the heartbeat minutes and `pm2 list` directly:** confirmed 2026-08-30 — `openwolf status` showed "Daemon: running" alongside "Last heartbeat: 40067 minutes ago" (~28 days stale), and `pm2 list` shows no `openwolf-daemon` process at all (only an unrelated `openwolf-mcp-api` entry). This broadens a 2026-08-26 finding that had scoped the "`.wolf/memory.md` stopped auto-updating" symptom to worktree sessions specifically — a plain main-checkout session (installing a plugin, editing a skill file directly, no worktree involved) also produced zero new `memory.md` entries. Don't trust `.wolf/memory.md` recency, or the status label alone, as a proxy for "the daemon is logging" — check `git log`/`gh pr list` directly, and treat this as an open `systematic-debugging` item (daemon appears to not be running, not just degraded).
- **Deliberate-shortcut ledger:** When cutting a real corner with a known
  ceiling (naive algorithm, global lock, skipped edge case), leave a
  `wolf-debt: <ceiling>, <upgrade trigger>` comment naming both. Harvest the
  ledger with the `debt-ledger` skill (`scripts/wolf-debt-scan.js`) so a
  deferral doesn't quietly become permanent. Digest for subagents:
  `hooks/subagent-thin-harness.md` (kept in sync with this bullet manually —
  no scripted check, only one duplicate exists).
- **Subagent routing:** Exploration spanning >3 files → spawn an Explore subagent (protects main context from search noise).
- **End of session:** invoke `session-reflect` — Phase 1 updates `.wolf/cerebrum.md` (always); Phase 2 conditionally audits CLAUDE.md for team-worthy learnings (approval-gated).
- **Skill observation log:** `.wolf/observations.md` is a separate, numbered/status-tracked (OPEN/ACTIONED/DECLINED) log for skill-library health — distinct from `cerebrum.md`/`memory.md`, which stay openwolf-daemon-owned (`openwolf init` creates them; the weekly `cerebrum-reflection` cron rewrites `cerebrum.md` wholesale) and must never be restructured. All reads/writes to `observations.md` go through `scripts/wolf-observation-log.js` (`append`/`resolve`/`archive` — JSON via stdin for `append`), never hand-edited or DOTALL-rewritten. `hooks/post-compact-observation.js` deterministically logs a per-session compaction checkpoint; `hooks/post-write-batch-nudge.js` reminds after 5 untracked file changes; `hooks/pre-principles-injection.js` injects `.wolf/cross-cutting-principles.md` before any `SKILL.md` edit. `session-reflect` Phase 3 runs the periodic review (7-day fallback) and applies observations via a two-tier rule: small additive changes → inline diff, approved, written live; substantial changes → `github-issue-first` → worktree → PR, same as any other non-trivial change.
- **Worktree path isolation:** `EnterWorktree` creates an isolated branch, but absolute-path edits still write to the MAIN working tree. Use relative paths or `cd <worktree-path>` before editing to isolate changes on the branch.
- **Plugin enable state lives in settings.json, not settings.local.json:** `claude plugin enable` writes the user-scope `"marketplace@plugin": true` flag to `settings.json`'s `enabledPlugins` map only — a same-key entry hand-added to `settings.local.json` is silently inert (`claude plugin list` still reports it disabled). Confirmed with `superpowers@superpowers-dev`, which had a stray `true` in `settings.local.json` doing nothing. Always use `claude plugin enable <name>` rather than hand-editing either file.
- **`claude plugin list` doesn't reflect a plugin enabled earlier in the same session:** confirmed installing `agent-stylebooks` — `settings.json` updated immediately (`"agent-stylebooks@agent-stylebooks": true`), but `claude plugin list` omitted it entirely, along with several already-enabled `claude-plugins-official@*` entries. Treat `settings.json` as authoritative when verifying a plugin enabled this session, not `claude plugin list`'s output.
- **Auto-mode classifier blocks direct edits to settings.json, not just git push/PR actions:** confirmed via repeated identical retries, all denied with the same generic "Blocked by classifier" reason and no added detail per retry — don't burn retries rewording the same call. Since the file controls permissions/hooks/plugins, edits are gated regardless of content. When blocked, hand the user the exact snippet to apply themselves, or ask them to add a permission rule first.
- **Global-install CLIs bypass worktree isolation:** third-party installers using a `--global`/home-anchored flag (e.g. `npx skills add ... --global`) resolve against the real `~/.claude` path regardless of `cwd` — confirmed with the taste-skill integration, where running the install from inside a worktree still wrote into the main checkout. After running one from inside a worktree, check `git status` in the main checkout too, and `mv` any new untracked files into the worktree before committing rather than assuming the install landed on the branch. Same phenomenon, different command class: `claude plugin enable/disable <name>` also resolves at user scope by default and writes straight to the live main checkout's `settings.json`, not the worktree's copy — confirmed while wiring the adhd-caveman hook (PR #59), where a `plugin disable` run from inside a worktree silently disabled a plugin live, mid-branch. Worse than an untracked-file surprise, since it's an immediate change to the user's actual running config — surface it to the user rather than assuming it's branch-scoped. Same class again: `claude plugins init <name> --with agents` scaffolds a placeholder top-level `SKILL.md` and `agents/example.md`, both left as unedited "TODO" stubs — these don't match the working reference pattern (`ba-agent`'s actual shape has only `.claude-plugin/plugin.json` + `agents/<name>.md`, no top-level skill file). Delete both stubs rather than committing them. Same CLI family, one more side effect: `npx skills add <repo> --skill <name> --global --copy -y` also writes a duplicate to `~/.agents/skills/<name>` (a separate, non-git home directory used by other agent tools) — expected, not a bug, and not something to clean up.
- **Worktree + gitignored plans:** `docs/superpowers/plans/` is gitignored (`plans/` in `.gitignore`) — plan files never get committed, unlike specs. A worktree created after `writing-plans` runs won't have the plan file at all (worktrees only see committed state), so `scripts/task-brief` fails with "no such plan file" until you `cp` the plan into the worktree's matching path right after `EnterWorktree`.
- **Subagent worktree-escape verification:** dispatched implementer subagents can silently escape worktree isolation — via an absolute path that resolves to the main checkout, or by attempting to self-modify `settings.json` permissions when a sandbox wall blocks a write (never comply with that; investigate the restriction or do the write directly in the main session instead). Give worktree-scoped dispatch prompts explicit relative-path-only instructions plus `pwd`/`git rev-parse --show-toplevel`/`git branch --show-current` checks before and after every write/commit, and independently re-verify the claimed commit's branch/parent (`git log --all`) from the controller side before trusting a DONE report. If escape is discovered after the fact, remediate non-destructively: `git reset --soft` (never `--hard`) to preserve unrelated concurrent daemon-driven `.wolf/*.md` changes, restore the affected file content, and remove only the specific stray artifacts — never a blanket reset of the main checkout.
- **Worktree merge pattern:** After committing in a worktree, `git checkout main` fails from inside it (main is checked out in the parent), and — now that branch protection is active — a local `git merge` into `main` would be rejected by GitHub on push anyway. Exit sequence: `ExitWorktree` (keep) → push the branch (`git push -u origin <branch>`) → `gh pr create` → wait for explicit user approval to merge (per CLAUDE.md §2's existing "never merge without an explicit yes" rule, unchanged) → `gh pr merge --squash` → `git -C ~/.claude pull origin main` → `git worktree remove .claude/worktrees/<name> --force` → `git branch -d <branch>`. **The `pull` step can fail** with "divergent branches" if local `main` has any commits not yet pushed to origin (routine here — specs/plans get committed to local `main` during brainstorming before ever being pushed). Confirm first with `git log origin/main..main`; if non-empty, use `git merge origin/main` instead of `pull` (safe when the squash-merged content is a superset of local `main`'s unpushed commits, which it will be if those commits are what the PR was built from) — never `reset --hard`, which would discard the unpushed local commits. The `git fetch origin main` behind that `git log`/`git merge` pair must run **after** `gh pr merge`, not reused from earlier in the session — a stale `origin/main` ref makes `git merge origin/main` silently report "Already up to date" without the PR's content ever landing on local `main`.
- **Stacked PR unmergeable after its base squash-merges:** if branch B was built on top of branch A (both open as separate PRs) and A merges via squash, retargeting B's PR to `main` shows `CONFLICTING` even though the content is identical — git can't recognize a squash commit as equivalent to the original commits it replaced. A plain `git rebase origin/main` on B tries to replay B's *entire* ancestor chain back to wherever B's branch actually forked (which can be far deeper than expected if the branch it forked from itself had stale local-vs-origin divergence baked in). Fix: `git rebase --onto origin/main <B's-real-fork-point-SHA> <B-branch-name>` — replays only B's own unique commits, skipping the ambiguous shared history entirely. Requires `git push --force-with-lease` afterward (real history rewrite).
- **Merging several independent PRs in one sequence invalidates every other open PR's "up to date" status on each merge**, when branch protection has `required_status_checks.strict=true` — `gh pr merge --squash` fails with "the head branch is not up to date with the base branch" for PR #2 immediately after PR #1 merges, even though PR #2's own CI was already green. Each remaining PR needs `gh api repos/<owner>/<repo>/pulls/<N>/update-branch -X PUT` before it's mergeable again — and if a third PR is still pending when the second merges, it needs updating again too. Expect up to N `update-branch` calls when merging N PRs in one session, not just one per PR.
- **Stash conflicts on worktree-merge cleanup:** if `git merge origin/main` refuses ("local changes would be overwritten") because the main checkout has pre-existing unrelated uncommitted drift in files your PR also touched, stash with a unique tagged message, capture its SHA (`git stash list --format='%H %gs'`), merge, then reapply by that exact SHA (`git stash apply <sha>`, never bare `pop`). Resolve conflicts by file type: append-only logs (`memory.md`) get both blocks concatenated in chronological order; wholesale-regenerated inventories (`anatomy.md`) get `git checkout --ours` + a fresh `openwolf scan` rather than a hand-merge. Drop only the stash entry matching your own tag — never touch other stash entries from concurrent sessions.
- **EnterWorktree branches from origin, not local main:** `EnterWorktree`'s default `worktree.baseRef` (`fresh`) branches from `origin/<default-branch>`, not local `main` — so any local-only commits on `main` not yet pushed (see above) are invisible in a freshly created worktree, and `docs/superpowers/specs/*.md` committed earlier in the same session won't be present until reconciled. Fix locally with `git rebase main` from inside the worktree (no push needed) right after `EnterWorktree`, before the first `task-brief` call.
- **Submodule commit transfer (worktree → main):** worktrees get independent submodule clones — a commit made in one is invisible to the other. To land it: create a named branch at that commit in the source clone, then from the target clone `git fetch <path-to-source-submodule-clone> <branch-name>` and `git branch -f local-customizations FETCH_HEAD`. A raw SHA is not fetchable via plain local-path fetch. `scripts/submodule-transfer.sh <submodule-path> <source-worktree-root> <commit-sha>` automates this.
- **Submodules aren't auto-initialized in fresh worktrees:** a new worktree (native `EnterWorktree` or `git worktree add`) leaves submodule directories empty until `git submodule update --init <name>` runs. A task touching a submodule-backed file (many skills are symlinks into `superpowers/`) can silently end up committing in the primary checkout instead of the isolated copy if this isn't checked first — verify `git -C <submodule> branch --show-current` before dispatching such a task in a worktree.
- **Hook/settings.json changes are not live mid-worktree:** edits to `settings.json` (or any hook file) made inside a worktree do NOT affect that running session — hooks were already loaded from the main checkout's `settings.json` at session start. Verify new hook behavior (e.g. spawning a probe subagent) only after merging into main, not mid-branch.
- **Skill symlinks / MCP registration are not live mid-session either:** a skill's `SKILL.md` existing on disk isn't enough — it must be symlinked into `~/.claude/skills/<name>` (every superpowers skill follows `skills/<name> -> ../superpowers/skills/<name>`; `subagent-driven-development`, `executing-plans`, and `finishing-a-development-branch` had no symlink at all until 2026-07-27, causing "Unknown skill" that a prior session wrongly attributed to transient API flakiness — see `.wolf/buglog.json` bug-195). The Skill tool's available-skills list and the MCP server list (via ToolSearch) are both loaded once at session start, so creating a missing symlink or running `claude mcp add` mid-session doesn't make it invokable in that same session. Same-session workaround: `Read` the skill file directly and follow it manually; for an MCP server, call the underlying SDK/CLI directly instead of waiting for its tools to appear. Both work normally starting the next session.
- **Editing a skill doesn't republish `docs-site`:** `.github/workflows/deploy-docs.yml` only redeploys on pushes touching `docs-site/**` (or the workflow file itself) — a `skills/**`-only edit never triggers it, even though `docs-site/scripts/pull-skills.mjs` pulls skill content in on `predev`/`prebuild`. Published skill docs go stale until an unrelated `docs-site/` change lands. If a skill edit needs the published page current, touch a `docs-site/` file too, or run the sync + redeploy manually.
- **`CLAUDE_CWD` is a dead variable:** referenced via `${CLAUDE_CWD:-default}` in settings.json but never actually assigned — always resolves to its default regardless of session location. Use `CLAUDE_PROJECT_DIR` instead (the real, populated equivalent, used correctly in `.wolf/hooks/shared.js`).
- **Concurrent sessions:** Edit/Write on a `.wolf/` file or `CLAUDE.md` repeatedly failing with "file changed since read" signals another live session. Use small targeted `Edit` calls scoped to untouched lines, or ask the user. `.wolf/memory.md` entries near your own timestamps aren't necessarily yours — verify via `git log`/`gh pr list`/`gh issue list` rather than the shared log alone when concurrent activity is suspected.
- **Worktree scope:** `EnterWorktree` always targets the session's primary repo (`~/.claude`) — it can't target a secondary/"additional working directory" project. For those, use `git worktree add <path> -b <branch> origin/<base>` via Bash instead. A 2026-08-19 finding claimed it fails outright when the session launches from a non-repo parent directory (e.g. `~`, one level above `~/.claude`) — a 2026-09-06 session launched from that exact directory and it succeeded without issue. Try `EnterWorktree` first regardless of launch directory; fall back to plain `git worktree add` only if it actually errors.
- **Model routing:** Before Claude-tier routing, check whether a local model should handle the task instead (boilerplate drafts, high-volume triage, pre-summarizing oversized input, retrieval, reasoning sanity-checks) — routed via `scripts/local-model-call.sh --auto <category>`, which resolves the model live from `config/local-model-routing.json` against LM Studio and Ollama and hard-blocks rather than falling back to an oversized model. Vision/OCR has no local coverage on this machine (no eligible small model). Architecture, security, and anything user-facing always stays with Claude. Within Claude: Haiku for mechanical/log-inspection/single-file-lookup subagent work, Sonnet default, Opus for complex multi-file reasoning, **Fable for demanding reasoning and long-horizon agentic work when Opus at high effort still falls short** — not a default, expensive ($10/$50 per MTok vs. Opus 5.5's $4/$20). `Explore` and `statusline-setup` dispatches that name an explicit `model` above their cap are blocked by `hooks/pre-agent-tier-gate.js` (edit `config/claude-tier-limits.json` if a cap is wrong); a dispatch that omits `model` inherits the agent's own default, isn't checked, and is logged with `model: null`; every other subagent_type is audit-only. Default effort for routine work; extended thinking only for genuinely complex decisions — no tool-level effort parameter exists in this harness to enforce this mechanically. See `model-routing` skill for detail.
